# Bootstrap decisions

The architecture document requires repository hosting, license and release
identity to be **recorded at bootstrap**, not silently assumed. This file
records them.

| Decision | Value | Rationale |
| --- | --- | --- |
| Repository hosting | `https://github.com/OffworldNexus/tpmd` | Matches the sibling Tunnel Weaver repository (`github.com/OffworldNexus/tunnel-weaver`). |
| License | Apache-2.0 | Same license as Tunnel Weaver; permissive with an explicit patent grant. |
| Authors | `Offworld Nexus Authors` | Same as Tunnel Weaver. |
| Edition | 2024 | Same as Tunnel Weaver. |
| Minimum Rust | 1.98 | Same as Tunnel Weaver (`rust-version = "1.98"`). |
| Default branch | `develop` | Requested at bootstrap; feature work happens on `feature/<linear-id>-…` branches. |
| Release signing | Not yet decided | No releases in WVR-140; revisit at packaging (WVR-145…150). |

## WVR-141 decisions

| Decision | Value | Rationale |
| --- | --- | --- |
| Storage | **One SeaORM-managed SQLite file** for every backend, one table per mechanism, **WAL** journal | A device has several backends and the daemon picks one at run time; a single migrated schema and a cheap-to-clone `DatabaseConnection` beat per-backend databases. WAL avoids read/write blocking; the sidecars stay covered by the `0700` directory. |
| TPM transport | **Hand-rolled** TPM 2.0 marshalling over `/dev/tpmrm*`; **no libtss2** | Keeps the crate pure Rust: no C toolchain to build, cross-compiles and unit-tests anywhere, and `cargo deny` stays simple. The architecture document permits system libtss2 for 1.x, so this is stricter than required. |
| Device selection | Scan `/dev/tpmrm0`…`tpmrm15`, then `/dev/tpm0`; `TPMD_TPM_DEVICE` overrides | A machine can host more than one TPM; never assume `tpmrm0`. |
| Backend selection | Runtime registry + `can_be_used()` + strongest `default_level()`, `--backend` to force | Backends are compiled in per OS but must prove they work here; the dummy is the guaranteed fallback. |
| System mode | `--system` (or root) → `/run/tpmd/tpmd.sock` mode `0666`, `/var/lib/tpmd` | Reachability is not authorization; clients need no `tss` membership. Deployment, not the daemon, provisions the directory. |

## WVR-144 decisions

| Decision | Value | Rationale |
| --- | --- | --- |
| Backend name / levels | `windows-cng`; advertises **`hardware` only** | The only honest hardware claim on Windows is a non-exportable, TPM-backed Platform Crypto Provider key. A DPAPI-wrapped software key is *not* sealing, so there is no `sealed` rung to report; keyring/file arrive from WVR-151 and the dummy. |
| Custody check | Export policy must be `0` **and** `PCP_PLATFORM_TYPE` must report TPM 2.0 | "DPAPI alone is not proof of TPM-backed sealing": the level is read back from the provider, never inferred from its name. A key that fails either check is **destroyed** and the provision returns `backend_unavailable`. |
| Usability proof | A live probe key at every daemon start (create → sign → export public → delete), cached | The ticket requires ordinary-user key creation to be *verified*: opening the provider succeeds over a network logon while key creation is refused, so a provider-only check would select an unusable backend. |
| Key context | The owning user's **interactive** session; machine keys are not used | Matches the acceptance ("owning user's context", "no elevation") and the macOS LaunchAgent precedent. Per-user keys live in the user's CNG store; `LocalSystem` cannot use them. |
| Agent shape | Silent per-user process, no window, started at logon (mechanism owned by WVR-149) | A service as `LocalSystem` cannot use a user's keys; a systray icon is optional UX and belongs to packaging. |
| Observability | `tpmd status` (client-side, all platforms) | A silent process still has to be answerable: this is the first-class "is it running, and what can it do?" check, alongside Task Manager, the per-user pipe and the state directory. |
| `unsafe` | Scoped exemption for one `ffi` module, using `windows-sys` (`Win32_Security_Cryptography`) | CNG is an OS component (nothing bundled); confining all FFI to one module keeps the rest of the crate safe code, mirroring `tpmd-ipc`'s `winutil`. |
| Rig toolchain | rustup + **MSVC** via VS Build Tools on the Windows 11 VM | Matches what CI and shipping builds use (`x86_64-pc-windows-msvc`). |

## WVR-151 decisions

| Decision | Value | Rationale |
| --- | --- | --- |
| Crate line | `keyring-core` + one store crate per OS (`zbus-secret-service`, `apple-native`, `windows-native`), target-gated | The `keyring` crate cannot satisfy the ticket at any version: v4's own docs tell applications that choose stores per platform to link `keyring-core` plus store crates, and v3's `linux-native` is the *kernel* keyring — the exact store the ticket excludes. `keyring-core` + zbus keeps the whole line pure Rust (no C toolchain, no libdbus), and `dbus-secret-service` is unused for that reason. |
| Build gating | Built on **every** OS, unlike the hardware backends; the *store* is target-gated inside the crate | All three platforms have a credential store, so "is this backend built?" is always yes; "is this host's store reachable?" is a run-time question (`can_be_used()`), which is exactly the build-time/run-time split the registry already draws. No Cargo feature is introduced anywhere. |
| Level | Advertises **`keyring` only** | The scalar is held by the OS store but signing is software. Claiming `sealed`/`hardware` would be a lie; claiming `file` would understate it. |
| Store address | `(principal, namespace, key_id)` folded into the store's *user* half, length-prefixed | The store's namespace is flat `(service, user)`, so the triple must be folded injectively: plain concatenation would let a namespace containing the delimiter collide with a different principal. Length prefixes keep it readable in the store's own UI, and the exact address is persisted so a future scheme change cannot orphan keys. |
| Secret encoding | Hex **text**, not raw bytes | The Secret Service implementation some desktops ship (KDE Wallet) is UTF-8 only, so an arbitrary binary secret cannot be written through it. |
| Metadata | New `keyring_keys` table + migration (one table per mechanism) | Ownership has to be decided *before* the store is touched, and the exact entry address has to be recorded; it also separates "row present, credential gone" (`key_loss`) from "no row" (`unknown_key`). |
| Windows persistence | Creation asks for the store's `persistence = Local` and **fails** if the host refuses it — there is no second, weaker attempt | The store defaults to `Enterprise`, which roams with a roaming profile — wrong for something whose whole purpose is to identify *this* device. A logon session with no profile-backed credential manager (a Task Scheduler- or service-started process, i.e. how the Windows agent runs) *refuses* durable persistence with `ERROR_NO_SUCH_LOGON_SESSION`: measured on the Windows 11 rig, where `Local` and `Enterprise` both returned 1312 while `Session` succeeded, and where `cmdkey` succeeded only because it writes session-persistable credentials. Falling back to `Session` was tried first and rejected: it silently changes the promise the level makes — the key would evaporate at logoff, the device would return as a stranger needing re-pairing, and a background service's log is not where a caller finds that out. The refusal is surfaced instead, and it counts as *gone* rather than *closed* because nothing the user does in that session changes it; the fix is how the agent is started (WVR-149). |
| Ownership | Row lookup first, store second | A request under the wrong principal must be indistinguishable from a request for a key that was never minted, so the store must never be consulted for a foreign key. |
| Usability probe | Once at open: build the store and ask one read-only question; `NoEntry` **and** `NoStorageAccess` both count as usable | `NoEntry` is the ordinary state before a key exists, so it cannot mean "unusable". Falling through to the dummy whenever the store is *locked* would silently weaken custody to a plaintext file, so a locked store is deliberately left to fail per operation as `store_locked` — which is what it does. Measured on macOS: a read of a missing item needs no unlock at all, so the probe still answers, and a write against a locked keychain fails in about a second with an authorization error rather than waiting for one. |
| Selection | An unreachable store makes the backend unusable → ladder falls through to `dummy` and records why; `--backend keyring` is still honoured | Headless hosts (no session bus) must keep working, but an operator who explicitly asks for the keyring should be told `store_locked` rather than get a refusal to start. This is the one place where forcing an unusable backend is not refused, hence `Backend::forced_when_unusable`. |
| Store mechanism in `status` | The *value* of the existing free-form `Status.backend` (`keyring (secret-service)`), via `Backend::store_mechanism()` | Names the underlying store where the ticket asks for it without touching the wire type, the protocol version or `tpmd-client`. `WELCOME.capabilities.backend` keeps the bare name for machine matching. |
| Threading | Every store call on a thread with **no** async runtime context, serialised by a process-wide lock; a store that answered is kept for the process's life | Tokio enters the runtime context on `spawn_blocking` threads, and the Linux store's blocking API builds its own runtime and calls `block_on` — which panics there. Its `Drop` disconnects the same way, so the store is never dropped. |
| `unsafe` | None added | Unlike the CNG backend, no FFI of our own is needed: the stores are pure Rust (`zbus`) or OS frameworks reached through safe wrappers. |

## WVR-152 decisions

| Decision | Value | Rationale |
| --- | --- | --- |
| Closed vs gone | Two conditions, told apart by **who can change them**, and classified by the backend by probing existence | A locked keychain is a state the user changes; a missing device node is not. Nothing else distinguishes them usefully, and error text differs per platform and per provider — it has misled before (`cmdkey` succeeding while `CredWrite` refused). |
| The closed answer | A new, **non-fatal** `CLOSED` message; `REJECT` stays fatal | A user-session store is shut normally, so "not now" must be distinguishable from "you spoke nonsense" without closing the socket. Reusing `REJECT` would have made the two indistinguishable. |
| Waiting | `AWAIT`, an `Op` with **no timing**, answered by `Reply::Opened` through the existing `Response` | Detection belongs to the daemon — it knows its dependency — so a client should not be handed an interval to poll on. Reusing `Op`/`Reply` keeps `id` correlation, pipelining and out-of-order answers working, and grew the protocol by one message, one reject code, one op and one reply. |
| Gone backends | A new `RejectCode::BackendUnavailable`, fatal, with its own client error variant | Retrying cannot fix a missing dependency, and rule 12 requires applications be told to warn their user rather than to try again. Giving it its own variant stops it being lumped with a transport failure. |
| Detection | One watcher per daemon process, woken by `Backend::unlock_hints()`; a real Linux bus signal, a backoff interval elsewhere, and a 5 s safety net on Linux | Ten parked clients must not mean ten probe loops, and a daemon with nobody waiting must poll nothing. A hint is never a promise, so every one is followed by a probe. |
| No version bump | `PROTOCOL_VERSION` stays **1** | tpmd is 0.1.0 and has never been released: there is no peer to be compatible with, and every addition here is an append, so existing frames are byte-identical. `docs/protocol.md` §6 says the shape is unstable until the first release; the first *released* change is when the bump becomes real. |
| Selection | A **closed** backend is a candidate; a **gone** one is skipped with its reason | Falling to a plainer store because a keychain happens to be locked is a silent custody change. This is also why `can_be_used()` kept its narrow meaning ("usable now") and the ladder asks `store_status()` instead. |
| Store state on the wire | `StoreState` on `Capabilities` and `Status`; the same `Closed` shape as the message | `tpmd status` should answer "is it running, and can it sign right now?" without attempting an operation, and a client should parse one shape rather than two. |
| Concurrency | Requests are dispatched as tasks and answers written by a writer task | A parked `AWAIT` must not stop the connection: the protocol allows pipelined requests and out-of-order answers, and rule 9 lets a waiting client ask `STATUS`. |

## WVR-153 decisions

| Decision | Value | Rationale |
| --- | --- | --- |
| Selection is sticky | The backend is chosen once, recorded in the shared store's `settings` table (`backend.selection`), and never changed by the daemon | Re-running the ladder every start let the store serving a device change because a keychain happened to be locked at boot — a custody change, and potentially an *identity* change, since a different store means a different key and pairing again. It is `select_level`'s principle one level up: one place decides, and not silently. |
| When it is recorded | On the first **successful use**, not at open | Opening a backend only proves it can be probed. A start that answers liveness probes and nothing else has chosen nothing, and `status` says `chosen_unix: null` — which is what stops a store that merely happened to be locked at startup from settling the machine on a weaker one. |
| Closed rungs | A backend whose store is merely **closed** is a candidate, never skipped | Otherwise the first start (at logon, before anything is unlocked) would permanently commit a plaintext store as this machine's identity. |
| What the record holds | Backend name, chosen-at, why, and what was passed over with reasons, `postcard`-encoded | "Why this backend?" is a question asked long after the fact, and the reasons contain whatever the platform said — colons, commas and all. A text column would have forced an escaping scheme; the wire's own vocabulary does not. |
| `--backend` | On a machine that has chosen: must agree with the record, or the daemon **refuses to start** naming `tpmd backend set`. On a machine that has not: it restricts the ladder to that rung | A flag that silently overrode the record would be the automatic change this ticket exists to prevent, wearing a command-line coat. |
| Administrator's verbs | `tpmd backend` (show), `tpmd backend set <name> --yes`, `tpmd backend clear` | Changing the backend can re-key the device, so it is deliberate, confirmed, and says what it costs. The record is read at startup, so a change takes effect at the next start — documented rather than surprising. |
| Stronger rung available | Reported in `status` as `selection.stronger_available`, **as information** | An administrator should know what they could adopt, but adopting it re-keys the device: information is the whole of the daemon's role here. |
| Store naming error | A record naming a backend this build does not have is refused on write (`tpmd backend set` validates), not discovered at startup | Better to refuse the change than to leave a machine whose agent will not start. |
| Recorded backend that cannot serve | Started anyway, and answers `closed` / `backend_unavailable` | Which is the point of WVR-152: a store that is temporarily shut is a state to report and wait on, not a reason for the daemon to refuse to exist. If the backend cannot even be *constructed* (a missing TPM device node), startup fails loudly rather than swapping in something weaker. |

## WVR-142 decisions

| Decision | Value | Rationale |
| --- | --- | --- |
| Levels on macOS | `keyring` (WVR-151) and `hardware` (Secure Enclave) only — no `sealed` | Settled, not deferred: every candidate for a macOS `sealed` is either already `keyring` (a login-keychain item, portable given the user's password) or `hardware` plus a user-presence policy — which this backend refuses to impose, because a prompt on an unattended agent is a hang rather than a security win. A level the platform cannot back would be a claim rather than a guarantee, and inventing one quietly is how a security level stops meaning anything. Windows reasons the same way from the other side, refusing to call a DPAPI-wrapped key sealing. Consequence: an unusable enclave falls to `keyring`, below the default `sealed` floor, so clients are refused unless they explicitly consent. |
| The agent is a signed `.app` whose executable **is** the daemon | `packaging/macos`, built by fastlane `bundle_agent` | The entitlements live on the executable, so a launcher that exec'd a separately signed binary would lose them; and a plain `codesign` of the same entitlement without a profile is killed at exec by AMFI. Measured: `codesign` itself only works in the Aqua session (`errSecInternalComponent` from SSH). |
| The bundle identifier must be **provisioned** | Configuration (`TPMD_BUNDLE_ID`), never a literal in the crate | Measured the hard way: with a profile but an identifier the team had not provisioned (`net.offworld.nexus.tpmd`), *storing* a key was refused with `errSecMissingEntitlement (-34018)` while the signature and profile looked perfect. With a provisioned one (`nexus.offworld.tpmd`) it works. It is a deployment's business, not the repository's. |
| Usability is probed by **storing**, not by generating | `probe_storage` at `open`, cached; the recurring probe asks the cheaper enclave question | An *ephemeral* enclave key is created happily from any session, including an SSH login, while keeping one is refused outside Aqua — so a generate-only probe reports a store that can never keep a key. The recurring probe must not write (WVR-152's rule), so it uses the ephemeral question and re-asks the storage one only until it has ever succeeded. |
| `Closed` versus `Gone` | `-25308`/`-25293` (interaction refused) → `Closed`, waitable; `-34018` (the process is refused) → `Gone`, and never re-probed | Only the first is the user's to fix by unlocking; the second is the signature's, and the process cannot change its own. Reporting the second as closed would park a client on a store that can never open — the failure WVR-152 exists to prevent. |
| No user-presence policy | `privateKeyUsage` + `AccessibleWhenUnlockedThisDeviceOnly`, no biometry or passcode | A prompt on an unattended agent is a hang, not a security win. What protects the login keychain still applies; the ticket is explicit that no presence policy is imposed. |
| Non-exportability is **enforced**, not documented | After creating a key, the private half is asked for; if the platform ever yields it, the key is deleted and provisioning is refused | The level's whole claim is that the key cannot leave. CNG's backend learned the same lesson (`private_export_is_refused`), and this is the macOS form of it. |
| Safe bindings only | `security-framework` 3.7 (+ its non-default `OSX_10_15` feature) and `core-foundation`; no `unsafe` anywhere | The API surface was verified to reach the enclave, so this backend needs no third scoped FFI module and stays under `#![deny(unsafe_code)]` like everything but the two documented exceptions. |
| macOS signature format | The enclave signs the SHA-256 **digest** (one hash, as §10 requires); DER is converted to raw `r ‖ s` here | Matches the other hardware backends and the wire; verified under `p256` with a mutated digest and a mutated signature both rejected. |

## WVR-146 decisions

| Decision | Value | Rationale |
| --- | --- | --- |
| The nightly repository | Cloudsmith's free Open-Source plan: it hosts, indexes and GPG-signs the archive, and CI only pushes a `.deb` | The comparison was against building the archive ourselves (a bucket or Pages plus our own signing key, index generation and nightly pruning) or having a service build it (OBS, Launchpad PPAs). Both of the latter are impossible — see the toolchain row — and the former is three permanent pieces of infrastructure for one package. The cost is accepted and stated: the apt URL is Cloudsmith's rather than ours, and their OSS policy wants an attribution badge. |
| One artifact per architecture, not per release | Built on the oldest supported release's glibc, published as `any-distro/any-version`, with a container install matrix proving the six releases | The daemon's only runtime dependency is glibc: the TPM transport is hand-rolled over `/dev/tpmrm*`, `zbus` is pure Rust over a socket, SQLite is bundled. One artifact per release would be six times the build for no additional truth, since the only thing that can differ between the build host and an install host is the libc floor. |
| Binary-only, built by our CI | `debian/` follows the Rust Team's policy in shape, but the Rust build takes a pinned toolchain from `packaging/deb/Dockerfile` rather than the distribution's | Measured, not assumed: rustc **1.90.0 builds this workspace** (all targets) and rustc **1.85.0 does not** — it dies inside `ctutils`, pulled in by the pinned `p256` line, before reaching our code. Every supported release is at or below 1.85 (bookworm 1.63, jammy 1.66, noble 1.75, trixie and 26.04 1.85), so a `Build-Depends` on the toolchain is unsatisfiable everywhere, and no amount of lowering the declared MSRV changes that. The declaration itself was stale — `rust-version = "1.98"` where the true floor is 1.94, set by `sea-orm`/`sqlx` rather than by our code — and is corrected in this same change rather than deferred, so the pin in `packaging/deb/Dockerfile` and every figure quoted here agree. |
| Source packages published, and the binaries built from them | `build-source.sh` makes one native `.dsc` + `.tar.xz` from a `git archive` of the commit with every crate vendored; every architecture's binaries are built from that `.dsc`, offline (`--network none` in CI), and both are pushed to the same component | The Cloudsmith setup script writes a `deb-src` line, so without sources every user's `apt-get update` warns about a missing `Sources` index — and a published binary whose source is not published beside it cannot be audited or rebuilt. Building the binaries *from* the published source makes it complete by construction rather than by review. Native, single-tarball because Cloudsmith rejects multi-component source packages (an `orig-vendor` component is what Debian would use). Vendored crates keep their `Cargo.lock`-tied package checksum but lose the per-file lists, as debcargo does, because dpkg-source drops `*.a`/`*.so`/`.gitignore` from a native tarball unconditionally. `debian/rules` now defaults to the split, so rebuilding the published source yields the published three packages. |
| Nightlies pruned to the newest seven versions; stable kept for ever | `packaging/deb/prune-nightlies.py`, run by the workflow's `prune` job after `verify` on nightly runs only; Cloudsmith's built-in retention rule stays disabled | The built-in rule counts *files* (one nightly is seven: three packages × two architectures plus the source) and cannot tell a complete version from a half-published one, so "seven nightlies" would be a number to re-derive every time a package or architecture is added, and a broken run would push good versions out. The script groups by version, orders with `dpkg --compare-versions`, deletes a version whole, only ever touches versions containing `~nightly`, and runs only after the new nightly installed on every release. |
| The system socket | `/run/tpmd/tpmd.sock`, created by systemd via `tpmd.socket`, handed to the service with `Sockets=` | `/run` is `root:root 0755`, so a daemon running as an unprivileged user cannot create anything in it; `RuntimeDirectory=tpmd` gives it a directory of its own. Moving the socket under it is therefore what makes running unprivileged possible at all — and it is the default on every Linux target, not a Debian detail, because the path is the contract between a client and a daemon and RPM and Arch inherit it unchanged. Socket activation additionally means a client reaching a cold machine is queued rather than refused. `listenfd` reads the handover so no `unsafe` enters `tpmd-ipc` for it. |
| The service user | `tss`, the standard TPM access identity, with no capabilities at all | Root was never acceptable for a process holding key material, and a new `tpmd` user would need the TPM device permission re-plumbed. `tss` already has it. The package ships a `sysusers` file that creates the user where the TPM userspace has not (systemd refuses to start a unit whose `User=` does not resolve), and a udev rule granting `/dev/tpmrm*` to that group, which is a no-op wherever the TPM packages' own rule is present. |
| The floor is not a start-up gate | The daemon starts and refuses individual operations below `--min-key-security`; `Restart=on-failure` therefore cannot loop on a missing TPM | It was tempting to promise "refuses to start without a TPM", which would have been false and would have produced exactly the restart storm the promise implies. What the documentation promises instead is true: the service comes up, `tpmd status` reports the level actually achieved, and key operations fail with the required and available levels named. |
| Removal and purge keep the store | `apt remove` and `apt purge` both preserve `/var/lib/tpmd` | A device identity is not a package artifact, and WVR-145 already asks for it: keys survive unless destruction is explicitly selected. Deleting the store is `rm -rf`, documented as irreversible and as re-pairing the machine. |
| `TPMD_STATE_DIR` and `TPMD_MIN_SECURITY` are real environment variables | Wired through clap's `env`, so `/etc/default/tpmd` configures the service | The state directory already honoured `TPMD_STATE_DIR` in user mode, but system mode took its path from a constant, so the documented configuration file would have silently ignored the one setting it most needs to carry. The floor had no environment spelling at all. Both are the same value the flag sets — one source of truth, two ways to reach it. |
| Backends as loadable plugins | Shipped: `tpmd` carries only the `file` floor, and one package per backend ships a `cdylib` into `/usr/lib/tpmd/backends`, loaded at run time (WVR-156) | The split costs a `dlopen` loader (a third scoped `unsafe` module against the rule in `AGENTS.md`) and a versioned plugin ABI; it buys packaging granularity, so that a machine installs only the mechanisms it has. It is a build mode rather than the default: a plain `cargo build` still links every backend in, which is what keeps the workspace's own tests independent of the plugin boundary. |
| How a plugin's code is driven | On a runtime of its own, `tpmd-plugin::runtime`, installed by the export macro; the store stays where it is (WVR-156) | The first split build aborted the daemon on startup, whichever plugins were installed. A `cdylib` links its own `tokio`/`sqlx`, and a runtime context is a thread-local of the crate that set it, so plugin code polled on the daemon's runtime found no runtime at all and `sqlx` aborted the process from inside a `cdylib` frame. The alternative — the daemon owning the store and the plugin owning only the mechanism — was rejected: `keyring` and `linux-tpm` both read *and write* the shared SQLite file, so it would rewrite both backends and the trait they implement to solve a question about which thread a future is polled on. |



`tpmd` deliberately shares the Tunnel Weaver cryptographic line so signatures
produced by the agent verify with `weaver_mux::auth::verify` byte-for-byte:

- `p256 0.14` (ECDSA P-256 / SHA-256), `postcard 1.1`, `serde 1.0`,
  `thiserror 2.0`, `tokio 1.43`, `proptest 1.11`, `cargo-deny` configuration.

## Scope

WVR-140 implements the **dummy** engine and the complete consumer contract.
WVR-141 adds the Linux TPM backend, WVR-144 the Windows CNG backend and the
`tpmd status` command, and WVR-151 the universal OS-credential-store backend.
The macOS Secure Enclave backend (WVR-142) and packaging and distribution
(WVR-145…150) are sibling tickets.
